# dante-input tests

- A test that binds fixed UDP/TCP ports keeps every port below Linux's ephemeral range (32768-60999). Ports in that range collide with any outbound socket on the CI runner ("Address already in use"). That failure blocked the v0.4.7 release.
- Since dlink v0.6.118 (dstack #264) the flow ports default to the device's slot block in 29800-31847. A device whose ARC port is no slot's (4440-4471) must set both `rx_port_base` and `tx_port_base`, or it does not start. The tests use ARC 24440/24441, so they set both inside 29800-31847, below the ephemeral range (`tests/device_e2e.rs` 31000/31032 and 31100/31132, the CI module test 31200/31232). Deployed configs leave both unset.

# dante-input latency

- Since v0.4.27 (dlink v0.6.106, dstack #244) the latency is named terms: `network_latency_ms` (a) + `receive_buffer_ms` (b) = the Dante latency P, plus each direction's app hand-off (c). `latency_ms` is gone and refused (strict file). Neither term set keeps P as before (13.041666 ms at 96/48 RX only). `InputConfig::split` maps dlink's ns refusal to the file's keys. obs never states latency numbers itself: quote dlink's own start-log lines (`dante-input dlink: ... dlink latency: ...`) or dstack. A dlink pin bump can break the API (budget_ns was removed): run `cargo clippy --all-targets` before pushing.

# dante-input CPUs

- dante-input.toml has no CPU keys. The owner ruled CPU-core pinning for dlink apps out (dstack#1, 4.11.2026). v0.4.11 had `pump_cpu`/`rx_cpu`, and v0.4.12 removed them. Because of `deny_unknown_fields`, a file that still sets them is refused at load.

# dante-input status line

- camera-box's E2E program-audio gate parses the `dante-input status:` line by token name. A new token goes at the END, after the last one (v0.4.26 appended `wire_late wake_delay_us wake_delay_peak_us` after `max_obs_us`). Never reorder or rename a token. `the_line_carries_every_contract_field_in_order` pins the whole line, and `tests/device_e2e.rs` checks the tokens on a real device.
- dlink's per-flow reads are per slot (`media.rx.lane(slot)` for 0..32). The line sums the counts and takes the worst slot for delays (`Status::flow`). A `last_*` value is dlink's last heartbeat second, not the print interval.
- v0.4.27 appended the TX tokens `tx_track tx_played tx_underruns tx_recentres tx_overflows tx_ppm tx_priming` (obs#41). They read 0 on a device without TX.
- v0.4.29 appended `rx_reordered` (obs#45, dlink v0.6.125, dstack #278): packets that filled a hole another packet opened. Since that pin `rx_gaps`/`rx_loss` count only holes still open at playout, so a reorder is no longer loss. dlink logs the wake delay's minute p50/p99/p99.9/max and the network latency itself (`RX flow timing in the last minute`); they are not tokens.
- Since dlink v0.6.148 (obs#67, dstack#326) the engine pump drains the RX sockets and writes the rings itself (normal profile): `rx_holes` = `rx_written_late` bursts on a loaded strih were the RX helper thread writing behind the reader. `wake_delay_us`/`wake_delay_peak_us` and dlink's write delay now include the wait for the next pump block (up to one block, ~2.7 ms at 128 frames/48 kHz) where they were tens of µs: a higher reading after that pin is not a regression.
- v0.4.30 appended `start_holes` (obs#47, dlink v0.6.126, dstack #234; camera-box asked for that name, no `rx_` prefix): ring samples read before the flow's first sample, the OBS-start burst. `rx_holes` holds only a running flow's holes since then. dlink logs `RX holes in the last minute ...` per flow and the write delay on the timing line itself.
- v0.4.37 appended `tx_resyncs` (obs#56, dlink v0.6.136, dstack#303): TX blocks that did not start where the last ended, re-primed by dlink's player. `TxOut::fill` passes each piece's start (`Block::start()` + the frames before it) to `Player::fill_at`; `fill_with` never resyncs.
- v0.4.39 appended `play_at_steps play_at_max_dev_us stamp_jumps gaps_unfilled` (obs#57's gate counters: dlink v0.6.137's PumpView, dante-input's Feed). `test_clock_ppm` (±50, TEST ONLY) puts the device on dlink's skewed system clock for the CI soak with `dstack-dev peer` (dstack docs/ci-peer.md); it is refused unless the environment sets `DANTE_INPUT_TEST_CLOCK=1` (only the soak step does), and a device on it logs a `TEST CLOCK` WARN. The soak's peer binary is checked against `plugins/dante-input/ci/dstack-dev.pin` (move it with the dlink pin).
- v0.4.41 appended `tx_late_pushes tx_push_gap_max_us` (obs#56, `tx::Cadence`): OBS's TX pushes over 1.5 times the last push's audio length after it (since the start), and the largest gap between two pushes since the last status line, µs, the gap still open since the last push included (a stall shows before its next push; only the push ending it counts it late, once). Only the status loop takes the window (`status_of(…, take = true)`); `DanteInput::status()` peeks. They tell a late writer (OBS's audio thread) from a reader-side underrun: the FIFO holds one chunk + one block, so a writer ~20 ms late empties it. The cause is dlink's (dstack#303): OBS's write landing ~10 ms late in its audio pass (a slow output before it) hit the bridge Player's floor re-centre, a ~22 ms dropout though the FIFO still held audio; `a_push_ten_ms_late_does_not_underrun_or_recentre` keeps it. v0.6.140 removed the re-centre but showed a second fault: the player reads the FIFO depth every 128 input frames, OBS writes 1024 on an exact grid, the readings alias and jump ~every 444 s at 6 ppm (tx_ppm 0.0 for minutes, then ramps to 30-40 ppm). The soak passes or fails on that by timing (v0.6.140: one fail, one pass): read the tx_ppm timeline, never trust one green soak of a TX change. dlink v0.6.143 stamps the FIFO writes and steers on the producer line; v0.6.144 (dstack #317) adds `Player::new`'s `producer_chunk_ns` (`chunk_ns(OBS_CHUNK_FRAMES, obs_rate)`). A simulation of the TX must build its FIFO with `Fifo::with_clock` (`tx_on`) and set that clock to each push's and block's simulated time, or the stamps say the writer ran far too fast. The soak runs OBS with FIXED 0 ms audio buffering (`~/.camera-box/genlock-audio-buffering-ms`, as stream-snv) and prints the cadence; it does not gate on it.

# dante-input audio stamps

- Since v0.4.34 (obs#53, dlink v0.6.132, dstack#295) each chunk handed to OBS is stamped with dlink's per-block play time (`Block::play_at`, os_gettime_ns's clock) plus the frames before it in the block. The pump queues `(first frame, play time)` beside the sample ring and the feeder stamps from it; `timestamp_ns` 0 (no media clock yet) makes plugin.c use `os_gettime_ns()`.
- `rx_stamps = "count"` (v0.4.35, obs#56) switches to a sample count from the first play time, for the dstack#303 bisect only. Never stamp by a sample count from a start point in production: the Dante media clock and CLOCK_MONOTONIC run ~6 ppm apart (21 ms an hour on stream-snv), and this fork's ASRC places a directly stamped source exactly at its stamp (STAMP basis), so any stamp re-anchor is an A/V step (camera-box issue 1527). Since v0.4.35 a skip in the blocks' media time (`Block::start()` jumps forward by G app frames, blocks the engine skipped, G up to `GAP_FILL_MAX_FRAMES` = 9600, bounded so the write on the pump thread stays far under a block period) is filled with G silent frames before the block; a block the full ring drops is filled by the next block; a fill the ring cannot take counts `gaps_unfilled`, so OBS's timeline stays contiguous; detect skips by `start()`, never by `play_at` (its clock-pair jitter would insert false silence). A backward or larger jump is a restarted schedule, not filled. A persistent stamp error of 10 ms or more for 1 s is slewed in by the ASRC at 1 ms/s (asrc-compensator.h `ASRC_PLACE_*`, `ASRC_STEP_RECOVER_PPM`). A chunk more than 1 ms off its continuation is a WARN `dante-input timing: a block's play time is … its continuation`.

# dante-input TX

- `tx` sends one OBS track (`tx_track`, from 1) on the same device (obs#41). OBS's mix runs on OBS's clock and Dante on PTP, so the mix goes through `dlink::bridge`: plugin.c's raw audio callback writes the `Fifo` on OBS's audio thread, and `TxOut::fill` reads it through the ASRC `Player` in the pump. Do not write a ring or a converter of our own.
- plugin.c untaps the raw audio callback (`stop_tx`) before `dante_input_stop`, so no push reaches a stopped device. `test/module_test.c running-tx` checks the order.
- With TX, the TX path is the TX hand-off (W + converter) + P; W is dlink's `WORK_MARGIN_NS` unless set. The TX bridge's FIFO is the app buffer (dlink v0.6.112, dstack #247): `Config::app_buffer(chunk_ns(OBS_CHUNK_FRAMES, obs rate), None)` in `InputConfig::dlink`, and `bridge_buffer()` goes to `Player::new`. That is OBS's 1024-frame chunk + one pump block, 22.667 ms on a 96 kHz device. `Split::tx_path_ns` excludes it, so OBS to the wire = tx_path + app buffer (the start line's `obs_to_wire_ns`).
- `tests/device_e2e.rs` serializes its devices (`ONE_DEVICE`): two devices in one test process at once would share the PTP follower and ports. Locally run it on a harmless interface (`DANTE_INPUT_TEST_IFACE=docker0 DANTE_INPUT_TEST_IP=172.17.0.1`), never on the Dante VLAN.

# dante-input soak

- The soak's tone fixture (`test/module_test.c` `tone_loop`) pushes each 10 ms block 20 ms before its stamp. With FIXED 0 ms audio buffering, OBS's mix tick leaves out a source whose buffer does not cover the tick (`obs-audio.c` `audio_buffer_insufficient`: `audio_pending`, no log), so a block pushed exactly at its stamp turned a host blip into one OBS tick of silence at the peer (24 ms = 2048 samples at 96k + ~256 converter edge; obs#56, dstack#303). A peer tone break with the peer's RX holes at 0 is silence that went in before dlink.
- The soak keeps the artifact `soak-evidence` (30 days): the peer's full log, its `peer.json` once a second (UTC), a stall witness (1 ms sleeps woken >5 ms late) and the control's log. Read it before blaming a side for a tone break. A break before the window opens is not counted by the gate: check the peer log's `a tone break` lines too.
- Since v0.4.45 (obs#71, dstack#354) dante-input logs each engine-pump wake one block or more late as a WARN `dante-input pump: a late wake at <UTC ms> behind <us> us (re-bootstrapped: blocks lost | within the margin)` (dlink's `Media::engine_stats().wakes().recent()`, at most 16 a status window; a wake is known by its time, lateness and outcome, so a wall-clock step neither hides nor repeats one, and wakes the pump's 32-wake ring dropped before the read are counted from `late_wakes()`), and once a minute `the last minute's latest wake`. The soak tees its run to `soak.log` (in `soak-evidence`) and `ci/soak_verdict.py` sets each peer tone break in the run beside them: `RUNNER: engine pump descheduled X ms at T` (a wake -50..+250 ms before the break's START, its report time less its length: the peer reports a break when the tone returns; the runner held the pump, rerun) or `OURS` (no wake: look at obs/dlink). The run fails either way. Run 43953607643 (v0.6.155, main) failed twice on pump wakes 6-8.6 ms late plus overruns of a 2 ms block; the stall witness (1 ms sleeps over 5 ms late) cannot see one thread descheduled alone.
- Since v0.4.46 (dlink v0.6.159, dstack#354) dlink's pump-watch warning splits each lost second: `oversleep_max_us` (the sleep returned late: the scheduler), `drain_max_us`/`drain_max_datagrams` (the per-block socket drain, ~2 µs a datagram), `max_process_cpu_us` (the largest block's thread CPU; `-` unmeasured). `soak_verdict.py` prints `== the pump's lost seconds`: a late wake is RUNNER when the oversleep is at least half the lateness; an overrun / `writes_after_send` over 10 × 56 µs is RUNNER only when the stall witness saw a host stall in that second (`--stall-log`), else `UNPROVEN` (steal or ours: never a silent rerun); at or under it, OURS. Never judge a block by cpu ≈ wall on the runner: GitHub's ubuntu runners are Azure (Hyper-V) VMs whose kernel has no paravirt steal accounting, so `CLOCK_THREAD_CPUTIME_ID` counts host steal as the thread's CPU (run 43990478131: 1.5-3.2 ms blocks with cpu = wall). On a quiet host obs's block is p50 26 / max 56 µs, also through a re-bootstrap + Rated restart + TX resync (dstack#354).
- A tone break is judged in order: a pump late wake or a dlink `the TX schedule starts again` line just before its start (RUNNER: our TX thread ran past the receivers' latency, late packets dropped by design), a `kind=misplaced` break -100 ms..+2 s before the TEST PEER's own pump-watch skip (its second boundary can fall inside a short break) (PEER: dstack#358, the peer's skip reads as one 2-sample misplaced break), else OURS. The module test's log lines carry a UTC ms time (`[level] <UTC>Z ...`) for that match; OBS itself prefixes its log lines with local time, so production lines are not changed. The stall witness logs wakes over 1 ms late (5 ms missed single-thread gaps).
- Since v0.4.46 (dlink v0.6.161, dstack#358) the test peer re-locks at its own pump's skip and counts it in `peer.own_skips`, never in `tone_gaps`; the soak gates `own_skips` rise 0 (a peer or runner stall still voids the window) and the verdict lists the peer's `its own reads jumped` lines as PEER. dstack's `tools/linux/tests/ci_peer_gate.py` (witness + void + re-measure up to 3 windows) is the fuller recipe (docs/ci-peer.md).
